1 Component delta

flowchart LR
  AG["agent (key)"] --> MW["C-11 auth middleware"]
  MW --> SUBAPI["C-15 subscription routes"]
  MW --> SSE["C-16 SSE stream"]
  SSE --> CAP["C-17 stream cap"]
  SUBAPI --> DB[("C-5 subscriptions")]
  SSE --> DB
  SSE --> ART[("articles by seq")]
  SINK["sink (writer)"] --> ART
  ART -->|"trigger: NOTIFY"| LST["C-18 listener"]
  LST -->|"wake"| SSE
  ADM["admin token"] --> ADR["C-14 admin list"]
  ADR --> DB
Check:
  • Is the NOTIFY only a wake-up, never the data a stream emits?
  • Does the stream read only committed articles, written solely by the sink?
  • Is the cap (C-17) consulted before any DB work?
  • Is the filter applied in exactly one place (the SQL query)?

2 Subscribe, stream, reconnect

sequenceDiagram
  participant G as Agent
  participant A as API (C-11/C-15/C-16)
  participant D as Postgres
  G->>A: POST /api/subscriptions {filter}
  A->>D: insert subscription
  A-->>G: 201 id
  G->>A: GET /stream (key)
  A->>D: stored cursor? first-run window?
  loop on each wake-up
    D-->>A: NOTIFY articles_new (after commit)
    A->>D: articles seq > last, filter
    A-->>G: id=cursor, event=article, data
  end
  A-->>G: ": ping" (keep-alive tick, key re-check)
  G--xA: connection drops
  G->>A: GET /stream, Last-Event-ID
  A-->>G: only articles after that id
Check:
  • Can an article fall between the last sent id and the resume point, even if a NOTIFY is lost?
  • Does the stream ever write agent_cursors?
  • What does the agent see if the key is revoked right after a ping?

4 Stream lifecycle

stateDiagram-v2
  [*] --> Rejected: no key / not own / bad id / over cap
  [*] --> Open: authorized, slot acquired
  Open --> Open: events and keep-alive
  Open --> Closed: client disconnects
  Open --> Closed: key revoked or agent disabled
  Open --> Closed: subscription deleted
  Closed --> [*]: slot released
  Rejected --> [*]
Check:
  • Is the slot released on every path into Closed?
  • Is Rejected always decided before the first event byte?
