2 Request a code, send it after the response (F-21, F-22, F-24)

sequenceDiagram
  participant U as User (web)
  participant A as API (C-43)
  participant L as Limiter (C-45)
  participant B as Background job
  participant D as Postgres (C-42)
  participant M as Mailer (C-44)
  U->>A: GET /api/auth/options
  A-->>U: password_reset_enabled
  U->>A: POST forgot-password {email}
  A->>L: attempt(address, email)
  alt over a limit
    A-->>U: 429 + Retry-After
  else allowed
    A-)B: schedule issue_and_send(email)
    A-->>U: 202 {"ok": true}
    B->>D: find user by email
    alt unknown email
      B->>B: stop (nothing stored, nothing sent)
    else known
      B->>D: upsert code hash, delete expired
      B->>M: send(code)
      M--xB: MailError (SMTP down)
      B->>D: discard the unsent code, log
    end
  end
Check:
  • Does the foreground (everything before the 202) do the same work for known and unknown emails (AC-3)?
  • Is the 202 sent before any database write or SMTP call (AC-1)?
  • Does a failed send leave no usable code behind (AC-14)?
  • Are unknown emails counted by the limiter like known ones (AC-11)?

3 Reset with the code (F-23)

sequenceDiagram
  participant U as User (web)
  participant A as API (C-43)
  participant R as Rules (C-41)
  participant D as Postgres (C-42)
  U->>A: POST reset-password {email, code, password}
  A->>A: email format, password policy (422)
  A->>A: per-address attempt limit (429)
  A->>D: claim_attempt: attempts+1 where open, unexpired, below cap
  D-->>A: stored hash, or nothing
  A->>R: constant-time compare with the keyed hash
  alt nothing, wrong or malformed
    A-->>U: 400 invalid_or_expired_code
  else match
    A->>D: one transaction: delete code, set password, delete sessions
    A->>A: clear the login lockout
    A-->>U: 204
  end
Check:
  • Is the password policy checked before an attempt is counted (AC-10), and the address limit before any code is looked at (AC-17)?
  • Is every refusal the same 400, including unknown emails (AC-5, AC-6, AC-7)?
  • Can two parallel correct requests both succeed? (They must not: AC-5.)
  • Are all three effects of success in one transaction (AC-4, AC-9)?

4 Data model (new table)

erDiagram
  USERS ||--o| PASSWORD_RESETS : "at most one open code"
  USERS ||--o{ SESSIONS : "ended by a reset"
  USERS {
    uuid id PK
    text email
    text password_hash
  }
  PASSWORD_RESETS {
    uuid user_id PK
    text code_hash "keyed HMAC, never the code"
    timestamptz expires_at
    int attempts
    timestamptz created_at
  }
  SESSIONS {
    uuid user_id FK
    text token_hash
  }
Check:
  • Does the primary key on user_id make "a newer request replaces the older" a plain upsert (AC-8)?
  • Is there nothing in the table that is the code itself (AC-2)?
  • Does deleting a user remove the open code (cascade)?

5 Lifecycle of a code (F-25)

stateDiagram-v2
  [*] --> Open: request for a known email
  Open --> Open: wrong code (attempts + 1)
  Open --> Used: correct code (row deleted)
  Open --> Locked: attempts reach the cap
  Open --> Expired: lifetime passes
  Open --> Replaced: newer request (upsert)
  Replaced --> Open
  Locked --> Replaced: newer request
  Expired --> Replaced: newer request
  Used --> [*]
Check:
  • Can a Locked or Expired code ever be used again? (It must not.)
  • Does a newer request always give a fresh attempt budget (attempts back to 0)?
  • Is the only way out of Open on success the deletion of the row (AC-5)?
