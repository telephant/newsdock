2 Provision and one authenticated run

sequenceDiagram
  participant O as Owner
  participant A as API (C-14/C-11)
  participant D as Postgres
  participant G as Agent (C-7)
  O->>A: POST /api/admin/agents (admin token)
  A->>D: insert agent + key hash
  A-->>O: api_key (once)
  O->>G: key in .env
  G->>A: list_new_articles (Bearer key)
  A->>D: verify key, read cursor
  A-->>G: articles, next_cursor
  G->>A: submit_analysis x N
  G->>A: ack_cursor(next_cursor)
  A->>D: cursor = GREATEST(old, new)
Check:
  • If the agent crashes before ack_cursor, is the batch seen again?
  • Is the plaintext key ever stored or logged on the API side?
  • Does the agent still avoid any DB or Kafka route?

3 Data model (new tables)

erDiagram
  agents ||--o{ api_keys : has
  agents ||--o| agent_cursors : has
  agents ||--o{ analyses : "name = agent_name"
  agents { uuid id PK
    text name UK
    text status }
  api_keys { uuid id PK
    uuid agent_id FK
    text prefix UK
    text key_hash
    timestamptz revoked_at }
  agent_cursors { uuid agent_id PK
    bigint seq }
Check:
  • Is analyses.agent_name (text, no FK) acceptable, given names are unique and immutable?
  • Should one agent be allowed several active keys at once?

4 Key and agent lifecycle

stateDiagram-v2
  [*] --> Active: key issued
  Active --> Revoked: admin revokes key
  Active --> AgentDisabled: admin disables agent
  AgentDisabled --> Active: admin enables agent
  Revoked --> [*]
Check:
  • Do both Revoked and AgentDisabled give the same 401 to the caller?
  • Is a revoked key final (never re-enabled)?
